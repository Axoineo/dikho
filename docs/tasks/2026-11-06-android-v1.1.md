# Task: Android app V1.1.0

Status: built and tested on emulators against a fake backend. Nothing committed, deployed or published.
Owner: Dikho Global Media LLP
Started: 2026-11-06
Last updated: 2026-11-06

## Goal

The app feels native on a phone: a launcher icon no mask cuts, a smooth logo, an inbox
that fits the screen and stays fast with thousands of records, a Device Contacts module
with direct calling and template sending, voice notes, and a hardened release build.

## Why now

The owner's V1.1.0 brief, 2026-11-06. It reports cropped icons, a stuttering logo, an
inbox that runs out of frame, freezes from loading everything at once, and asks for new
device features.

## Non-goals

- Moving business rules into the app. `dikho-mobile/` stays free of them.
- Paid or real sends during testing, unless the owner asks for one.

## Decision

The app was a WebView shell (ADR 0011), and every complaint in the brief was about React
screens. The owner chose to build the inbox and drawer natively ("Build them natively"),
which ADR 0012 records. Every other module stays in the WebView for now. On 2026-11-06 the
owner also asked whether the whole app should go native: that is about 24,000 lines of
React, so the recommendation in ADR 0012 is to move module by module.

## Audit

Measured in Chrome with mobile emulation on the production bundle, against a scratch
backend with synthetic data. 6x CPU slowdown stands in for a mid-range phone. Production
row counts were not read: the count query was refused by the permission system, so the
tests use the API's own caps.

| Area | State |
| --- | --- |
| Horizontal overflow | 15 screens at 320 and 360 wide: only the open chat failed (fixed). Contacts scrolls sideways inside its box (680px table in 334px) |
| Touch targets | Composer 36px, chat header 40px, search 32px, filter tabs 28px, drawer rows 32 to 44px |
| Drawer | React. Flat list with two expanding groups, active highlight and account footer. No section headers, no swipe gesture |
| Launcher icon | Adaptive icon already separate (`mipmap-anydpi-v26/ic_launcher.xml`), no `flutter_launcher_icons`. Mark reached 38.9dp from centre against a 33dp safe circle and a 36dp round mask (fixed) |
| Logo | Flutter shows a static PNG and fetches nothing. The animation is the web splash in `index.html`, replayed by `BrandLoader` on the first visit to each lazy route. SVG mask and transform on the WebView's main thread while 548 KB of JS parses |
| Asset caching | Hash-named chunks are served `max-age=0, must-revalidate`, so every launch revalidates them |
| Inbox layout | Already one pane at a time below 768px. A phone held sideways gets rail, list and thread together (thread 235px at 844x390) |
| Conversations API | `LIMIT 200`, no paging, no server search: older chats cannot be reached or found. Refetched every 25 seconds |
| Thread API | 500 messages a page: 12,286 DOM nodes, opening a chat blocks the page 1.7s at 6x |
| Contacts API | 2,000 rows by default, up to 5,000: 22,227 DOM nodes, 4.9s to appear at 6x. The count reads 2,000 even when more exist |
| Template sending | `POST /whatsapp/conversations/:id/template` needs an existing conversation, and only inbound webhooks create them. Media headers and link buttons with variables are refused |
| Secrets | None. Source scan, plus 32 MB of the decompressed release APK including `libapp.so` and `classes.dex`: no Meta tokens, Supabase secret or service keys, JWTs, AWS or Stripe keys, private keys or signing passwords. No `.env` files; `pubspec.yaml` registers two PNGs. Signing key outside the repository |
| Session storage | WebView `localStorage`: app-private with backups off, not Keystore-encrypted. Flutter stores nothing |
| Logs | Two `debugPrint` calls behind a compile-time test flag, WebView console suppressed, no Kotlin logging |
| Shrinking | R8 and resource shrinking on. Dart not obfuscated: `CrmScreen`, `UpdateManager` readable in `libapp.so` |

## What was built

| Phase | Where |
| --- | --- |
| Icon | `res/drawable/ic_mark.xml`: mark inside the 33dp safe circle |
| Logo | `lib/features/splash/`: drawn from paths generated from `index.html`, one controller, `RepaintBoundary`. Nothing waits on the network |
| Drawer | `lib/features/shell/app_drawer.dart`: Material 3, grouped, from the permissions the page reports |
| Inbox | `lib/features/inbox/`: list, thread, composer, rich messages, media, realtime |
| API | `conversations.js`: paging, search, thread size, send to a number. Migration 0013 |
| Phone contacts | `lib/features/device_contacts/`, `DeviceFeatures.kt` |
| Voice notes | `VoiceRecorder.kt`, `VoicePlayer.kt`, `composer.dart` |
| Session | `src/lib/shellVault.js`, `session_vault.dart`: Keystore-encrypted |
| Updates | `update_manager.dart`, `update_schedule.dart`, `add-release.mjs --required` |
| Release | `proguard-rules.pro`, `build-release.sh`, `direct` and `play` flavours |
| Web | Leads details on phones, Contacts paging, route preloading, immutable assets |

## Decisions made

- 2026-11-06: The microphone header and the thread fix went ahead without waiting: both are
  needed under either option.
- 2026-11-06: Native inbox and drawer, by the owner (ADR 0012).
- 2026-11-07: The remaining modules move native one at a time, not all at once, by the owner.
  Order proposed: Leads, Clients, WhatsApp Dashboard and Templates, Contacts, Campaigns,
  Vendors with Sales and Purchase orders, Users and Settings, Email Hub. Leads done
  2026-11-07, Clients done 2026-11-09, both native and tested on the emulator. Templates
  and the WhatsApp dashboard done 2026-11-09, then WhatsApp Contacts the same day (the
  spreadsheet importer stays a web page the app opens), then Campaigns, then the native
  new-campaign wizard (owner: "Wizard after 0013"). The wizard is built and tested but
  must ship only after migration 0013 and the request-id fix are live: the live start has
  no duplicate guard. Vendors native the same day. Sales orders native 2026-11-12; its
  tax invoice PDF stays a web page (`/sales-orders/:id/invoice`) the app opens, so the web
  must deploy before that APK. Purchase orders native 2026-11-13; Vendors' New PO opens it.
  Found while building it: the web reads a sales order's lines by `sales_order_id` alone,
  so purchase order lines (which carry it too) show as its lines, on its tax invoice, and
  are rewritten by an edit; the native screens filter them out, and the web fix went to
  the session fixing the web Sales orders form. Next in the proposed order: Users and
  Settings, then Email Hub.
- 2026-11-09: The owner asked for a new WhatsApp dashboard with graphs and every analytic
  Meta's API offers, on the web and in the app, and for each campaign's own performance.
  Built: `GET /api/whatsapp/analytics` and `/analytics/campaigns/:id`, the web dashboard
  and `/whatsapp/campaigns/<id>`, and native screens for both. Meta's template insights
  are left off: turning them on is irreversible, so it is the owner's call.
- 2026-11-09: Button taps added. The owner chose not to switch template insights on; link
  taps show only if Meta answers. After deploying, the owner checks the dashboard: if
  link taps show (insights already on), remove `scripts/whatsapp/check-template-insights.mjs`
  as no longer needed.

- 2026-11-14: The owner wants the whole app native, sign-in included, with anything that
  does not convert redesigned for the phone, and plans to publish it on the Play Store,
  so it must be built secure and reliable to Play's rules. Proposed order: native
  sign-in and session first (email or WhatsApp code, my_access, session tracking and
  forced sign-out, idle sign-out), then Users and Settings, Live Assist (screen sharing
  redesigned for a phone), Email Hub, the phone redesigns (spreadsheet import, tax
  invoice PDF), removing the WebView, and the Play build (no self-update, permission
  disclosures, data safety, a reviewer sign-in that does not need a real inbox).

- 2026-11-17: The owner chose to go straight to a fully native Play Store release, with
  no staff APK release first. Order: finish sign-in (permissions, heartbeat, idle and
  admin sign-out in the app), Users, Settings, Live Assist, Email Hub, the phone
  redesigns (tax invoice PDF from the API, contacts import), remove the WebView, then the
  Play build and listing.
- 2026-11-17: Sign-in finished: the app signs in, owns the session and keeps its rules
  (access, heartbeat, idle and 8-hour sign-out, administrator sign-out); the page in the
  app no longer runs its own copies (ADR 0013). Emulator `signin` 6/6 and `orders` 6/6.
- 2026-11-17: Users native (people, profiles, access, sessions, templates, departments,
  audit log; the permission grid redesigned as a list per module). Live Assist is not on
  the native profile yet; it comes with Live Assist itself. Next: Settings.
- 2026-11-17: Settings native (profile, preferences, devices; company, regional, lists
  and media for `settings.manage`). The theme now comes from the person's profile in the
  app too. Open: native screens show dates in their own short form, not the
  organization's date format (amounts do follow the number style); the start page
  still works through the page's landing route and needs a native landing once the
  WebView goes. Next: Live Assist.
- 2026-11-17: Live Assist native, IN PROGRESS. Owner chose: a phone shares only
  Dikho's own screens (pictures of the app's top widget, a few a second, on a `frames`
  WebRTC data channel, no Android screen-recording permission), and helpers can help
  from a phone too. New dependency `flutter_webrtc: 1.6.3` (MIT, no manifest
  permissions of its own; merged manifest not yet checked). Written:
  `lib/features/live_assist/` (protocol, api, link, screen_frames, controller,
  widgets, helper viewer), root layer in `app.dart`, wiring in `crm_screen.dart`
  (staff events via `SessionGuard.onStaffEvent`), Live Assist button on native
  profiles; web: `frames.js` (+ test), viewer shows pictures, page skips its own
  Live Assist when the app lists `live-assist`. `test/live_assist_test.dart` 18/18.
- 2026-11-19: Live Assist native finished. ADR 0014, changelog and guide written;
  flutter_webrtc's Bluetooth and audio-settings permissions removed (audio routing only
  starts for a sound track, which Live Assist never has). Emulator `assist` 7/7 with
  headless Chrome as the helper; the fake server relays Realtime in both protocols.
  Found and fixed on the way: tooltips in the layer needed their own overlay, and the
  banner was hidden from screen readers by the routes' barrier. Not run: phone as the
  helper of a computer's video (needs a computer sharing a tab), a real network between
  two phones. Next: Email Hub.
- 2026-11-19: Email Hub part 1, the inbox, native: list, conversation (each message
  in a locked web view with a no-network, no-script policy; links asked about and
  opened in another app), attachments downloaded with the session through a new
  `keepFile` platform call, filing, status, assignee, notes, CRM records, and a
  composer redesigned for a phone (plain text, original quoted). Emulator `email` 6/6.
  Scenarios' web-page example moved to Email campaigns.
- 2026-11-19: Email Hub part 2, overview and analytics, native (reusing the WhatsApp
  dashboard's cards, tiles and labelled bars). Remaining: campaigns and templates,
  consent, settings (mailbox connection by Google sign-in needs an app link back from
  the browser).
- 2026-11-19: Email Hub part 3, campaigns and templates, native. A designed (HTML)
  email is never edited on the phone: it is shown read-only and can be replaced by a
  template; plain emails are written as text. Approval sends the fingerprint of the
  version shown, as the web does. Scenarios' web-page example moved to Consent.
  Remaining: consent, Email settings.
- 2026-11-19: Layout fixes seen in the emulator pictures: the save bar stacked its
  buttons on a 411dp phone (words now above, buttons on one line; one row from 600dp),
  and the send-time hint was cut off (hint caps raised). Widget tests that tap right
  after `scrollUntilVisible` must let the list stop first: a gliding list takes no taps.
- 2026-11-19: Email Hub part 4, consent, native: look up one address, record consent
  (how they agreed required) or an unsubscribe, suppress or lift. Owner's plan: Play
  Store later (organization account, D-U-N-S ready); first all native work, then the
  owner tests on a real phone. Scenarios' web-page example moved to Email settings.
  Remaining Email Hub part: Email settings.
- 2026-11-19: Email Hub part 5, Email settings, native; the Email Hub is now all
  native and so is every drawer entry. Google's return (/email/connect App Link) is
  finished by the app with its session; no API change. Scenarios: `email` and
