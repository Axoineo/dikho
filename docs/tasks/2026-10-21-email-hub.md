# Task: Email Hub

Status: active
Owner: Dikho engineering (implementation by Claude Code)
Started: 2026-10-21
Last updated: 2026-10-21

## Goal

A native Email module (Dikho CRM → Email) in which staff read and answer
their own and their team's Google Workspace mail beside the CRM record it
concerns, and the marketing team sends approved, consented campaigns. It must
never let a global permission, a developer role or database access stand in
for mailbox-level consent.

## Why now

Client and vendor conversations happen in Gmail, outside the CRM, so the
history of a deal lives in personal inboxes. Bulk email has no approval,
consent or suppression control today. Brevo sends only two system emails
(staff welcome, new-device alert).

## Non-goals

- Replacing Gmail as the store of mail. Gmail stays the source of truth.
- Storing message bodies or raw MIME in Supabase by default.
- A mail server, a VPS, a second user directory or a TypeScript migration.
- Changing MX records or any DNS without an explicit owner decision.
- Treating aliases or Google Groups as mailboxes with their own sign-in.

## Acceptance criteria

See the phase table below; each phase lists what "done" means. The overall
definition of done is the one in the original brief (Gmail OAuth, shared
mailbox ACL, recovering sync, send/reply, on-demand bodies, protected
attachments, CRM links, a delivering transactional provider, approved and
consented campaigns, controlled duplicates, reliable automations, accessible
UI, RLS and secret tests, no regressions, staged release).

## Phase 0 audit (2026-10-21)

### Repository

- Branch `claude/wizardly-maxwell-k00757`, clean tree, based on `main`
  (`8fff104`, PR #31).
- Stack confirmed against code: React 19 + Vite 8 SPA (JSX, React Router 7,
  CSS tokens in `src/index.css` with Tailwind 3 mapped onto them, preflight
  off), Hono 4 API Worker (`src/api/app.js`), Supabase Postgres/Auth,
  D1 + R2 for WhatsApp only. No `CLAUDE.md`; `AGENTS.md` is canonical.
- Auth: `requireAuth` calls `my_access()` with the caller's token on every
  request (live session, active staff, permission map); `requirePermission`
  gates routes. Owners and developers hold every permission, so a mailbox
  rule that relied on permissions alone would let any developer read mail.
- New modules (User Management, Live Assist) keep tables private to the
  service role and put every rule in `SECURITY DEFINER` functions the Worker
  calls with a verified actor. The Email Hub follows that pattern.
- Brevo: two senders, both plain `fetch` to `api.brevo.com/v3/smtp/email`:
  `src/api/services/staffWelcome.js` (Worker) and
  `supabase/functions/device-check/index.ts` (Edge Function).
- `aws4fetch` is already a dependency (unused by the app today); it signs
  SES v2 requests without an AWS SDK.
- Cron Triggers do not fire on the current Workers plan (verified
  2026-10-01, `docs/CONFIGURATION.md`). Queues also need the paid plan. Any
  scheduled work must be request-driven or come from an independently
  verified scheduler.
- CSP (`vite.config.js`, report-only today) allows images only from self,
  `data:`, `blob:` and the API origin. Email HTML is therefore rendered in a
  sandboxed iframe with its own CSP, and remote images stay blocked.
- Baseline before any change: `npm run lint` 0 errors (25 existing
  warnings), `npm test` 125/125, `npm run build` ok, `npm run scan:secrets`
  clean.

### Database (read-only, production, 2026-10-21)

- All 24 repository migrations are recorded as applied; nothing pending.
- Extensions installed: `pgcrypto`, `uuid-ossp`, `pg_stat_statements`,
  Vault. Available but not installed: `pg_cron`, `pg_net`, `pgmq`.
- Data volumes are small (tens of rows), so no performance shortcut is
  needed now; indexes are still designed for thousands of contacts.
- Audience fields that actually exist:
  - clients: `email`, `company_name`, `contact_person`, `city`, `state`,
    `country`, `status`. No industry, no media, no assigned salesperson.
  - vendors: `email`, `company_name`, `contact_person`, `vendor_type`,
    `status`, `media_id`/`sub_media_id` (media are exactly ATL, BTL, TTL),
    location through `vendor_addresses`.
  - corporate-gifting leads: `email`, `name`, `company_name`, `city`.
  - Not available anywhere: business industry, engagement status, assigned
    salesperson. These filters are not offered.
- Advisor findings outside this task (recorded, not changed):
  - `public.rls_auto_enable()` (an event-trigger function from the original
    schema) is `SECURITY DEFINER` and executable by `anon`. Calling an event
    trigger function directly fails, so it is not exploitable, but EXECUTE
    should be revoked from `anon`/`authenticated`.
  - Five finance trigger functions have a mutable `search_path`
    (`finance_touch_updated_at`, `prevent_void_payment_with_allocations`,
    `prevent_issued_invoice_mutation`, `prevent_issued_invoice_line_mutation`,
    `validate_payment_allocation`).
  - 23 unindexed foreign keys and three RLS policies that re-evaluate
    `auth.uid()` per row (`user_devices`, `login_events`, `document_events`).
  - Leaked-password protection is off (passwordless sign-in makes this low
    impact).

## Constraints and assumptions

- Google Workspace OAuth client is "Internal" (Workspace users only), so the
  restricted `gmail.modify` scope needs no Google security assessment. If the
  client is External, Google verification is required before production.
- `gmail.modify` is the narrowest single scope that reads, labels, archives,
  drafts and sends. The full `https://mail.google.com/` scope (permanent
  delete) is never requested.
- SES is not assumed ready: identity, production access, IAM, configuration
  set and SNS topic are all unverified. SES sends stay off until the owner
  confirms each.
- Consent: marketing campaigns go only to addresses with recorded opt-in
  consent (`subscribed`). A CRM record alone is not consent.

## Decisions made

- 2026-10-21: Mailbox access needs BOTH the `email_inbox.view` permission
  and a mailbox membership; Owners and developers get no implicit
  membership (ADR 0009).
- 2026-10-21: No one grants themselves mailbox access; personal mailboxes are
  delegated only by their owner (ADR 0009).
- 2026-10-21: Refresh tokens are encrypted in the Worker (AES-GCM, key in a
  Worker secret, bound to the account id) so database access alone cannot
  read anyone's mail (ADR 0009).

## Risks, blockers and rollback

- Blocker (owner): Google Cloud project with an Internal OAuth client,
  redirect URI on the API origin, Gmail API enabled, and (for push) a
  Pub/Sub topic + push subscription with an OIDC service account.
- Blocker (owner): SES identity verification, production access, IAM user
  limited to `ses:SendEmail` on the identity/configuration set, configuration
  set with an SNS event destination.
- Blocker (owner): authoritative DNS provider for `dikho.in` (Hostinger or
  Cloudflare) before any SPF/DKIM/DMARC/custom MAIL FROM change. MX stays on
  Google Workspace.
- Blocker (owner): a scheduler that runs without dashboard traffic. Options:
  enable `pg_cron` + `pg_net` to call a signed Worker endpoint, or move the
  API Worker to a plan where Cron Triggers fire, then re-run the probe.
- Rollback: the module is off unless `EMAIL_HUB_ENABLED=true`; migrations are
  additive and their tables can stay unused.
